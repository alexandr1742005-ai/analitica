# Non-Functional Requirements (NFR)

Версия: 1.0 | Статус: Approved

| ID | Категория | Требование | Метрика приёмки |
|---|---|---|---|
| NFR-01 | Производительность | Время автоматического скорингового решения | ≤ 5 секунд на заявку (p95) |
| NFR-02 | Производительность | Время отклика API для чтения статуса заявки | ≤ 300 мс (p95) |
| NFR-03 | Масштабируемость | Система должна выдерживать пиковую нагрузку | 200 заявок/минуту без деградации |
| NFR-04 | Доступность | Доступность платформы (uptime) | ≥ 99.5% в месяц (за исключением регламентных окон) |
| NFR-05 | Безопасность | Персональные данные (паспортные данные, доход) должны храниться в зашифрованном виде | AES-256 для данных at rest |
| NFR-06 | Безопасность | Передача данных между клиентом и сервером | Только по TLS 1.2+ |
| NFR-07 | Безопасность | Пароли пользователей хранятся только в виде хэша | bcrypt / argon2, соль индивидуальна |
| NFR-08 | Безопасность | Доступ к административным операциям (ручная проверка) — только для аутентифицированных операторов с ролью `operator` | RBAC, JWT с claim `role` |
| NFR-09 | Соответствие требованиям (Compliance) | Обработка персональных данных должна соответствовать 152-ФЗ «О персональных данных» | 100% полей ПДн промаркированы и защищены |
| NFR-10 | Соответствие требованиям | Условия кредита должны соответствовать ФЗ-353 «О потребительском кредите» | ПСК (полная стоимость кредита) рассчитывается и отображается клиенту |
| NFR-11 | Аудируемость | Все действия, изменяющие статус заявки/кредита, должны логироваться с указанием времени и инициатора | 100% покрытие критичных операций аудит-логом |
| NFR-12 | Usability | Форма подачи заявки должна быть пройдена клиентом без обращения в поддержку | ≥ 90% успешных самостоятельных подач в UAT |
| NFR-13 | Совместимость | Веб-интерфейс должен корректно отображаться в последних версиях Chrome, Firefox, Safari, Edge | Кросс-браузерное тестирование без критичных дефектов |
| NFR-14 | Отказоустойчивость | При недоступности внешнего условного БКИ система должна деградировать в режим ручной проверки, а не отказывать всем заявкам | Автоматический fallback в `MANUAL_REVIEW` |
| NFR-15 | Наблюдаемость (Observability) | Ключевые бизнес-метрики (кол-во заявок, конверсия, время скоринга) должны быть доступны в виде метрик/дашборда | Экспорт метрик в формате, пригодном для Grafana/Prometheus |
| NFR-16 | Резервное копирование | Резервное копирование базы данных | Ежедневный full backup, RPO ≤ 24ч, RTO ≤ 4ч |
| NFR-17 | Локализация | Интерфейс и сообщения об ошибках — на русском языке | 100% пользовательских сообщений локализованы |

## Связь NFR с архитектурными решениями

- **NFR-01, NFR-02** → скоринговый расчёт выполняется синхронно для простых случаев и асинхронно (очередь) при высокой нагрузке — см. Sequence Diagram.
- **NFR-05, NFR-06, NFR-07** → отражены в схеме БД (`password_hash`, отдельная таблица `Passports` с ограниченным доступом) и в OpenAPI (`security: bearerAuth`).
- **NFR-09, NFR-10** → отражены в BRD (раздел 6, бизнес-правила) и в полях таблицы `Loans` (`interest_rate`, `full_cost_of_credit` — при расширении).
- **NFR-14** → отражено в Use Case «Скоринг заявки», альтернативный поток «БКИ недоступно».

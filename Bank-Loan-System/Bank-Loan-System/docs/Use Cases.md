# Use Cases

Версия: 1.0 | Нотация: полное текстовое описание (Fully Dressed Use Case)

Акторы: **Клиент**, **Система (скоринговый модуль)**, **Оператор банка**, **Условное БКИ**.

---

## UC-01. Регистрация клиента

| Атрибут | Значение |
|---|---|
| Актор | Клиент |
| Предусловия | Клиент не имеет учётной записи |
| Постусловия (успех) | Создана учётная запись клиента со статусом `active` |
| Триггер | Клиент нажимает «Зарегистрироваться» |

**Основной поток:**
1. Клиент открывает форму регистрации.
2. Клиент вводит email, телефон, ФИО, дату рождения, пароль.
3. Система проверяет уникальность email/телефона (FR-02).
4. Система проверяет сложность пароля (FR-03).
5. Система создаёт запись в таблице `Users`.
6. Система возвращает подтверждение регистрации.

**Альтернативные потоки:**
- 3a. Email/телефон уже занят → система возвращает ошибку, поток завершается.
- 4a. Пароль не соответствует требованиям → система возвращает ошибку с указанием требований.

## UC-02. Идентификация клиента

| Атрибут | Значение |
|---|---|
| Актор | Клиент |
| Предусловия | Клиент аутентифицирован, идентификация не пройдена |
| Постусловия (успех) | Запись в `Passports` со статусом `verified = true` |
| Триггер | Клиент переходит к оформлению первой заявки |

**Основной поток:**
1. Клиент вводит паспортные данные (серия, номер, кем выдан, дата выдачи, место рождения).
2. Система валидирует формат данных (FR-12).
3. Система вычисляет возраст клиента и проверяет диапазон 21–65 лет (FR-11).
4. Система сохраняет данные в `Passports` со статусом `verified = true`.
5. Клиенту открывается доступ к разделу «Подать заявку».

**Альтернативные потоки:**
- 3a. Возраст вне диапазона → система отклоняет идентификацию, клиенту показывается объяснение.
- 2a. Некорректный формат паспортных данных → система запрашивает повторный ввод.

## UC-03. Подача заявки на кредит

| Атрибут | Значение |
|---|---|
| Актор | Клиент |
| Предусловия | Клиент идентифицирован, отсутствует активная просрочка > 30 дней |
| Постусловия (успех) | Заявка создана в статусе `SUBMITTED` |
| Триггер | Клиент заполняет форму заявки |

**Основной поток:**
1. Система проверяет отсутствие просрочки более 30 дней (BR-08).
2. Клиент указывает сумму, срок, цель кредита.
3. Система валидирует сумму (10 000–3 000 000 ₽) и срок (6–60 мес.).
4. Клиент прикладывает документы (справка о доходах).
5. Клиент подтверждает отправку заявки.
6. Система создаёт запись `LoanApplications` в статусе `SUBMITTED`.
7. Система инициирует Use Case UC-04 (Скоринг заявки).

**Альтернативные потоки:**
- 1a. Активная просрочка > 30 дней → система блокирует создание заявки (AC-06).
- 3a. Сумма/срок вне диапазона → система возвращает ошибку валидации.

**Расширения:** Клиент может сохранить заявку как черновик (`DRAFT`) и вернуться к ней позже (FR-26).

## UC-04. Скоринг заявки

| Атрибут | Значение |
|---|---|
| Актор | Система (скоринговый модуль), Условное БКИ |
| Предусловия | Заявка в статусе `SUBMITTED` |
| Постусловия (успех) | Заявка в статусе `APPROVED`, `DECLINED` или `MANUAL_REVIEW` |
| Триггер | Автоматически при переходе заявки в `SUBMITTED` |

**Основной поток:**
1. Система переводит заявку в статус `SCORING_IN_PROGRESS`.
2. Система запрашивает кредитную историю клиента в условном БКИ (`CreditHistory`).
3. Система рассчитывает скоринговый балл на основе дохода, возраста, стажа, количества открытых кредитов, наличия просрочек (FR-35).
4. Система применяет пороговые правила:
   - Балл ≥ 700 → статус `APPROVED`.
   - Балл < 400 → статус `DECLINED`.
   - Балл 400–699 → статус `MANUAL_REVIEW`.
5. Система сохраняет результат в `ScoringResults`.

**Альтернативные потоки:**
- 2a. БКИ недоступно (таймаут/ошибка) → система переводит заявку в `MANUAL_REVIEW` с причиной `BKI_UNAVAILABLE` (NFR-14).

## UC-05. Ручная проверка заявки

| Атрибут | Значение |
|---|---|
| Актор | Оператор банка |
| Предусловия | Заявка в статусе `MANUAL_REVIEW` |
| Постусловия (успех) | Заявка в статусе `APPROVED` или `DECLINED` |
| Триггер | Оператор открывает заявку из очереди |

**Основной поток:**
1. Оператор открывает список заявок в статусе `MANUAL_REVIEW`, отсортированных по дате подачи (FIFO).
2. Оператор изучает анкетные данные, документы и результат скоринга.
3. Оператор принимает решение: одобрить или отклонить.
4. Оператор указывает комментарий (обязателен при отказе).
5. Система обновляет статус заявки и фиксирует `operator_id`, время решения.

## UC-06. Подписание договора

| Атрибут | Значение |
|---|---|
| Актор | Клиент |
| Предусловия | Заявка в статусе `APPROVED` |
| Постусловия (успех) | Заявка в статусе `CONTRACT_SIGNED` |
| Триггер | Клиент открывает раздел «Подписать договор» |

**Основной поток:**
1. Система отображает клиенту условия кредита (сумма, срок, ставка, ПСК, график платежей).
2. Клиент запрашивает SMS-код подтверждения.
3. Клиент вводит полученный код.
4. Система проверяет корректность кода.
5. Система переводит заявку в статус `CONTRACT_SIGNED`.

**Альтернативные потоки:**
- 4a. Неверный код (до 3 попыток) → повторный ввод.
- 4b. Превышено число попыток → блокировка на 30 минут.

## UC-07. Выдача кредита

| Атрибут | Значение |
|---|---|
| Актор | Система |
| Предусловия | Заявка в статусе `CONTRACT_SIGNED` |
| Постусловия (успех) | Создан `Loan` в статусе `ACTIVE`, заявка в статусе `DISBURSED` |
| Триггер | Автоматически после UC-06 |

**Основной поток:**
1. Система создаёт запись в `Loans` (сумма, ставка, срок, дата выдачи, номер договора).
2. Система рассчитывает аннуитетный график платежей и создаёт записи в `Payments`.
3. Система эмулирует зачисление средств клиенту.
4. Система переводит заявку в статус `DISBURSED`.

## UC-08. Просмотр статуса кредита и истории платежей

| Атрибут | Значение |
|---|---|
| Актор | Клиент |
| Предусловия | Клиент аутентифицирован |
| Постусловия (успех) | Клиент видит актуальный статус заявок/кредитов |
| Триггер | Клиент открывает личный кабинет |

**Основной поток:**
1. Клиент открывает раздел «Мои заявки» или «Мои кредиты».
2. Система запрашивает данные из `LoanApplications`, `Loans`, `Payments`.
3. Система отображает статус, суммы, даты, график платежей.

# Functional Requirements (FR)

Версия: 1.0 | Статус: Approved | Связано с: BRD, User Stories, Acceptance Criteria, Use Cases, OpenAPI

Требования сгруппированы по модулям. Каждое требование имеет уникальный ID для трассировки в User Stories и Acceptance Criteria.

## Модуль 1. Регистрация и аутентификация

| ID | Требование | Приоритет |
|---|---|---|
| FR-01 | Система должна позволять клиенту зарегистрироваться, указав email, номер телефона, ФИО, дату рождения и пароль. | Must |
| FR-02 | Система должна проверять уникальность email и телефона при регистрации. | Must |
| FR-03 | Система должна требовать пароль длиной не менее 8 символов, содержащий цифры и буквы. | Must |
| FR-04 | Система должна позволять клиенту авторизоваться по email/телефону и паролю. | Must |
| FR-05 | Система должна блокировать учётную запись после 5 неудачных попыток входа на 15 минут. | Should |

## Модуль 2. Идентификация клиента

| ID | Требование | Приоритет |
|---|---|---|
| FR-10 | Система должна запрашивать паспортные данные клиента (серия, номер, кем выдан, дата выдачи, место рождения). | Must |
| FR-11 | Система должна проверять возраст клиента: заявка доступна только клиентам 21–65 лет (BR-04). | Must |
| FR-12 | Система должна выполнять базовую валидацию формата паспортных данных (контрольные символы, формат серии/номера). | Must |
| FR-13 | Система должна сохранять статус идентификации клиента (`verified` / `not verified`) в таблице `Passports`. | Must |
| FR-14 | Клиент не может подать заявку на кредит, не пройдя идентификацию (BR-01). | Must |

## Модуль 3. Подача заявки на кредит

| ID | Требование | Приоритет |
|---|---|---|
| FR-20 | Система должна позволять клиенту создать заявку с указанием суммы, срока и цели кредита. | Must |
| FR-21 | Система должна валидировать сумму кредита в диапазоне 10 000–3 000 000 ₽ (BR-02). | Must |
| FR-22 | Система должна валидировать срок кредита в диапазоне 6–60 месяцев (BR-03). | Must |
| FR-23 | Система должна запрещать подачу новой заявки клиенту с просрочкой более 30 дней (BR-08). | Must |
| FR-24 | Система должна позволять клиенту прикрепить документы (справка о доходах и т.д.) к заявке. | Must |
| FR-25 | Система должна присваивать заявке статус `DRAFT` при создании и `SUBMITTED` при отправке на рассмотрение. | Must |
| FR-26 | Система должна позволять клиенту редактировать заявку в статусе `DRAFT`. | Should |

## Модуль 4. Скоринг

| ID | Требование | Приоритет |
|---|---|---|
| FR-30 | Система должна автоматически рассчитывать скоринговый балл (0–999) после подачи заявки на основе анкетных данных и кредитной истории. | Must |
| FR-31 | Система должна автоматически одобрять заявки со скоринговым баллом ≥ 700 (BR-05). | Must |
| FR-32 | Система должна автоматически отклонять заявки со скоринговым баллом < 400 (BR-06). | Must |
| FR-33 | Система должна направлять заявки со скоринговым баллом 400–699 в очередь на ручную проверку (BR-07). | Must |
| FR-34 | Система должна сохранять результат скоринга (балл, решение, версию модели, дату) в таблице `ScoringResults`. | Must |
| FR-35 | Система должна учитывать при расчёте скоринга: доход, возраст, стаж, количество открытых кредитов, наличие текущих просрочек. | Must |

## Модуль 5. Ручная проверка (Manual Review)

| ID | Требование | Приоритет |
|---|---|---|
| FR-40 | Система должна предоставлять оператору интерфейс/API для просмотра заявок в статусе `MANUAL_REVIEW`. | Must |
| FR-41 | Оператор должен иметь возможность одобрить или отклонить заявку с указанием комментария. | Must |
| FR-42 | Система должна фиксировать ID оператора, принявшего решение, и время решения. | Must |

## Модуль 6. Договор и выдача кредита

| ID | Требование | Приоритет |
|---|---|---|
| FR-50 | Система должна инициировать процесс подписания договора после одобрения заявки. | Must |
| FR-51 | Система должна подтверждать подписание договора через SMS-код (эмуляция) (BR-09). | Must |
| FR-52 | Система должна создавать запись в таблице `Loans` после подписания договора со статусом `ACTIVE`. | Must |
| FR-53 | Система должна рассчитывать график платежей (аннуитетная схема) и сохранять его в `Payments`. | Must |
| FR-54 | Система должна переводить заявку в статус `DISBURSED` после эмуляции зачисления средств (BR-10). | Must |

## Модуль 7. Личный кабинет клиента

| ID | Требование | Приоритет |
|---|---|---|
| FR-60 | Клиент должен иметь возможность просмотреть статус своей заявки в реальном времени. | Must |
| FR-61 | Клиент должен иметь возможность просмотреть активные и закрытые кредиты. | Must |
| FR-62 | Клиент должен иметь возможность просмотреть график платежей и историю оплат. | Must |
| FR-63 | Клиент должен получать уведомление об изменении статуса заявки (email/push — эмуляция). | Should |

## Модуль 8. Аудит и безопасность

| ID | Требование | Приоритет |
|---|---|---|
| FR-70 | Система должна логировать все изменения статуса заявки с указанием времени и инициатора. | Must |
| FR-71 | Система должна хранить персональные данные клиента в зашифрованном виде (см. NFR). | Must |
| FR-72 | Доступ к данным клиента должен быть ограничен ролевой моделью (клиент видит только свои данные, оператор — данные назначенных заявок). | Must |
